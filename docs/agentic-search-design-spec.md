# Agentic Search 設計規範
**來源論文**：DCI（arXiv 2605.05242）× Grep Harness（arXiv 2605.15184）

---

## 核心洞見一句話

> **AI 搜尋的瓶頸不在「找到多少文件」，而在「找到之後能不能精準定位那句話」。**
> **決定準確率的，不只是搜尋演算法，而是整個執行框架（harness）的設計。**

---

## 一、兩種搜尋方式的根本差異

### 傳統向量搜尋（Vector / RAG）的運作方式

```
使用者問題
    ↓
把問題轉成數字向量
    ↓
在資料庫裡找「語意最相近」的前 k 份文件
    ↓
把這 k 份文件交給 AI 回答
```

**比喻**：像圖書館員把「和你問題主題相關」的書搬過來一疊，
但如果你要的那句話剛好被分在「相關性第 11 名」的書裡，你就永遠看不到它。

---

### DCI（直接語料庫互動）的運作方式

```
使用者問題
    ↓
AI 自己決定要搜什麼關鍵字
    ↓
用 grep / find 等工具直接在原始文件裡搜尋
    ↓
只取「命中位置前後幾行」，不讀整份文件
    ↓
沒找到就換關鍵字再搜，直到夠確定為止
    ↓
回答
```

**比喻**：你自己拿著手電筒在書庫裡找，
看到一本書就翻到那一頁，確認那句話真的在那裡，再拿去當證據。

![[2605_05242_fig_two_paradigms.png]]
*左：傳統 RAG，語料先壓縮成固定窗口再給 AI；右：DCI，AI 直接用工具操作原始語料*

## 二、最反直覺的數據：找得少，答得準

這是整個 DCI 論文最重要的一張表：

| 指標 | 向量搜尋 | DCI（grep） |
|------|---------|------------|
| 找到正確文件的比例（召回率） | **56.7%**（更高） | 28.0% |
| 找到文件後定位到關鍵句的精準度 | 21.7 | **48.4**（更高） |
| 最終回答正確率 | 45% | **73%** |

![[截圖 2026-05-10 中午12.40.24.png]]
*DCI 的召回率比向量搜尋低一半，但最終準確率高出 28 個百分點*

**結論**：與其找到 10 份文件但只能模糊地看，不如找到 3 份文件但能精確定位到第 47 行。

## 三、AI 實際上怎麼用 grep？

觀察 3,168 條指令，AI 的行為分佈：

| 指令模式 | 佔比 | 白話說明 |
|---------|------|---------|
| `rg "關鍵字" \| head` | **56.2%** | 搜很多結果，只看前幾筆，控制讀入量 |
| `rg "詞1" \| rg "詞2"` | **20.6%** | 串接兩個條件，像 AND 篩選 |
| `wc`（計數） | 7.8% | 先估一下有多少筆，再決定怎麼處理 |
| `rg "單一關鍵字"` | 6.3% | 直接搜 |
| `cat`（讀整份文件） | **0.1%** | 幾乎從不讀整份文件 |

**關鍵設計原則**：AI 把 grep 當作「高精準、低讀入量」的工具，永遠只取命中位置附近幾行，不是把整份文件丟進去。

## 四、AI 的六步搜尋策略（可直接對應工具設計）

![[Pasted image 20260510115629.png]]
*DCI agent 的搜尋行為分成 6 個階段*

| 階段 | 目的 | 實際指令 |
|------|------|---------|
| 1. 探索語料結構 | 先看資料長什麼樣 | `ls`, `find`, `head` |
| 2. 廣泛關鍵字搜尋 | 找出可能的候選文件 | `rg "關鍵詞" corpus` |
| 3. 逐步縮小範圍 | 結果太多時加條件 | `rg "詞1" \| rg "詞2"` |
| 4. 讀取候選文件局部 | 確認候選文件裡有沒有答案 | `cat file`, `head`, `sed` |
| 5. 在單一文件內深搜 | 在文件裡找更多線索 | `rg "term" file.txt` |
| 6. 跨文件比對 | 排除錯誤候選，確認唯一答案 | `rg "keyword" file1 file2` |

## 六、Harness 是比搜尋演算法更重要的變數

**Harness**（執行框架）= 決定 AI 能用哪些工具、怎麼呈現搜尋結果、何時停止搜尋的整套管理機制。

同樣是 Claude Opus 4.6 + grep，只換 harness 的框架：

| 框架 | 準確率 |
|------|--------|
| Chronos（有問題分類 + 動態指令） | **93.1%** |
| Claude Code（直接使用） | 76.7% |

**差了 16.4 個百分點，和換掉整個搜尋演算法的影響一樣大。**

![Image](https://pbs.twimg.com/media/HIlbuS_aAAAcqa9?format=png&name=large)
*同一個模型、同一個搜尋方式，不同框架的準確率差距*

Harness 影響的細節：
- **系統指令（prompt）設計**：有沒有依問題類型調整搜尋策略提示
- **結果呈現方式**：搜尋結果是直接放進對話（inline）還是寫到檔案再讓 AI 去讀（file-based）
- **迭代策略**：AI 能搜幾輪、怎麼判斷「夠了」
- **輸出處理**：terminal 輸出怎麼被切割、格式化後送給 AI

## 七、最重要的工程警告：不要用「先存檔再讀取」模式作預設

兩種結果呈現方式的差異：

**Inline（直接注入）**：搜尋結果 → 直接放進 AI 對話 context
**File-based（先存後讀）**：搜尋結果 → 存成檔案 → AI 再自己去開檔案讀

理論上，先存檔可以節省 context 空間。但實際測試：

| 模式 | GPT-5.4 + Codex 準確率 |
|------|----------------------|
| Inline grep | **93.1%** |
| File-based grep | **55.2%**（崩潰 -37.9%） |

![Image](https://pbs.twimg.com/media/HIlcNDvaMAALZSR?format=png&name=large)
*programmatic file-based 模式重排結果，反而讓強模型崩潰*

原因：file-based 模式要求 AI 完成「找到檔案 → 打開 → 讀取 → 整合」的多步工作流。
搜尋本身沒有問題，但整合階段的複雜度讓系統不穩定。

**規則：預設用 inline，context 真的不夠才考慮 file-based，且要先做穩定性測試。**

## 八、什麼題目用 grep，什麼題目用向量搜尋

| 問題類型 | 推薦策略 | 原因 |
|---------|---------|------|
| 日期、數字、人名、明確偏好 | **Grep 優先** | 答案通常就是那幾個字，直接命中 |
| 「什麼時候」「他說過」「有沒有提到 X」 | **Grep 優先** | 字面搜尋精準且快 |
| 跨多個來源的語意聚合 | **向量搜尋 + 補 grep** | 向量先召回候選，grep 再精準定位 |
| 措辭多樣的概念查詢 | **向量搜尋** | 可以找到「說法不同但意思一樣」的片段 |

![Image](https://pbs.twimg.com/media/HIlaHguaAAERiwn?format=jpg&name=large)

## 九、Context 管理策略（長對話搜尋的關鍵）

隨著搜尋輪數增加，對話歷史會越來越長。三種處理策略的效果：

| 策略 | 做法 | 準確率 |
|------|------|--------|
| L1：只截斷 | 每次工具輸出限制在固定字元數 | 較低 |
| **L3：截斷 + 壓縮** | 超過閾值後清除舊的工具輸出，只留佔位符 | **77%（最佳）** |
| L4：截斷 + 壓縮 + AI 摘要 | 再用 AI 重新摘要歷史 | 下降 |

![[截圖 2026-05-10 中午12.46.03.png]]
*context management ablation：L3 是最佳配置*

**適度忘記比完整記憶更好**：AI 在長程搜尋中，保留「最近的工作狀態」比保留「所有歷史結果」更有效。

## 十、規模上限：什麼時候 grep 會失效

![[截圖 2026-05-10 中午12.42.47.png]]
*語料庫規模對 DCI 準確率的影響*

| 語料規模 | DCI 準確率 | Tool 呼叫次數 |
|---------|-----------|-------------|
| 10 萬份文件 | 80.0% | ~40 次 |
| 20 萬份文件 | 66.4%（-13.6%） | 86.9 次（+117%） |
| 40 萬份文件 | 37.5%（崩潰） | 超過預算上限 |

**Arthur vault 目前數千份筆記，遠低於 10 萬份的上限，可以直接套用純 grep 策略，不需要 embedding index。**

## 十一、設計決策總表

| 決策點 | 結論 | 理由 |
|--------|------|------|
| 搜尋方式 | **Grep 為主** | vault 規模適合，精準度優於向量 |
| 結果呈現 | **Inline delivery** | file-based 不穩定，可致 -37.9% |
| Context 管理 | **L3（截斷 + 壓縮）** | 最佳準確率，不需 LLM 摘要開銷 |
| 工具粒度 | **Bounded snippet，不給整份文件** | AI 的 0.1% cat 使用率說明沒必要 |
| 問題分類 | **按題型切換策略** | 同一 harness 不同策略差距達 16.4% |
| 模型選擇 | **能力越強，DCI 優勢越大** | Sonnet 4.6 vs. nano：83% vs. 68% |

## 十二、Arthur KG 系統的對應架構

```
輸入問題
│
├─ 問題分類
│   ├─ 字面事實（日期/數字/人名/偏好）→ Grep 搜尋
│   ├─ 時序推理 → Grep + 模型推理
│   └─ 語意聚合（多文件交叉）→ Vector 初篩 → Grep 精準定位
│
├─ DCI 搜尋（工具層）
│   ├─ search_entity(name)          → rg "name" vault/
│   ├─ grep_relation(keyword)       → rg "keyword" --glob='*.md'
│   ├─ chain_filter(k1, k2)         → rg "k1" | rg "k2"
│   ├─ inspect_snippet(file, term)  → rg -n "term" file | head
│   └─ count_candidates(keyword)    → rg "keyword" | wc -l
│
├─ Inline delivery（結果直接注入 context）
│
├─ Context 管理：L3（截斷 + 壓縮）
│
└─ 答案生成 + 引用原始筆記路徑
```

**規模**：遠低於 10 萬份上限，不需要預建 embedding index
