# 論文筆記格式規範

每次整理 AI / 技術論文筆記，必須遵循以下結構。
核心原則：**先說清楚問題是什麼，再說方法，再說實驗，最後說發現與意義。**

> **語言、圖片判斷、速查表格式、正文條列化規範**見 CLAUDE.md 全域規範，本文不重複。

---

## 整體結構順序

```
1.  Frontmatter
2.  TL;DR（列點式，放在 frontmatter 正下方）
3.  一、研究背景與動機（目前困難、領域缺口）
4.  二、核心演算法直覺（白話 + 流程圖 + 對比表）
5.  三、方法細節（超參數、公式、變體）
6.  四、實驗結果（benchmark 數字、對比表）
7.  五、主要發現（3–5 個子節，以反直覺或最重要的結論命名）
8.  六、關鍵圖表解讀（每張圖一個條目）
9.  七、侷限與風險
10. 八、延伸應用
11. 九、落地設計（選填）— Arthur 自己的系統設計延伸
12. 附：關鍵數據速查表
```

**章節編號規範**：
- 主章節用中文數字：`# 一、` `# 二、` ... `# 九、`
- 子節用阿拉伯數字，對應主章節：`## 1.1` `## 1.2`、`## 2.1` `## 2.2`
- 範例：`# 二、核心演算法直覺` → `## 2.1 核心概念` → `## 2.2 演算法流程`

**必寫章節**：一 到 八 共 8 章全部必須出現，不得跳過。九（落地設計）選填。

**四條禁止規則**：
1. **章節順序不可調換**：必須嚴格按照一 → 二 → 三 → 四 → 五 → 六 → 七 → 八的順序輸出，不得把任何章節提前或延後。
2. **`# 二、` 只能有三個子節**：`## 2.1 核心概念`、`## 2.2 演算法流程`、`## 2.3 與舊方法最大的不同`。Case study、bash command 分佈、應用啟發一律不屬於 `二、`，應放到 `五、`、`六、`、`八、`、`九、`。
3. **圖片說明整合進對應章節，不集中在六章**：每張圖的條列說明（圖在說什麼／關鍵數字／為什麼／Takeaway）緊接在該章節的圖片後方。`# 六、` 只寫一行索引（「Fig 1–2 → 2.1，Fig 3–4 → 5.1…」），不重複解讀內容。
4. **同張圖禁止重複嵌入**：每張圖片（同一 `![[filename]]`）在整篇筆記中只能出現一次，放在最有助於理解的位置；其餘章節用「見 Figure N」文字引用。

> [!note] 設計邏輯
> 先說困難讓讀者理解「為什麼要有這篇論文」，再說方法與實驗讓讀者看懂「它怎麼做」，最後說發現與圖表讓讀者抓到「它告訴了我們什麼」，結尾才是「我能用它做什麼」。

## 1. Frontmatter（必填）

```yaml
---
title: 中文標題（論文名稱直譯或意譯皆可）
date: YYYY-MM-DD（arXiv 發布日期）
source: 會議/期刊名稱（如 ICLR 2026、arXiv）
authors: 第一作者, 第二作者 et al.（機構）
sector: 研究領域（如 LLM 推理 / 向量量化 / RL）
tags:
  - 核心技術1
  - 核心技術2
url: arXiv 或論文連結
---
```

**注意**：`authors` 欄位寫作者姓名（非 `speaker`），機構放括號內。若有多個連結（如知乎中文解析），加 `url_zh:` 欄位。

---

## 2. TL;DR（必寫，放在 frontmatter 正下方）

列點式，包含以下列點：

```markdown
## TL;DR

- **核心主張**：[方法名] 用「[核心做法]」解決 [問題]
- **關鍵機制**：為什麼這樣做有效（可展開子列點說明技術細節）
- **核心數字**：關鍵指標的具體數字（如 Pass@3 從 0.523 → 0.560，+3.7%）
- **適用條件 / 限制**：什麼情況下有效、什麼情況下不適用
```

若論文沒有可量化結果（純理論），`核心數字` 改為 `核心貢獻`：

```markdown
- **核心貢獻**：提出「[核心機制]」，解決 [具體問題]，貢獻在於 [1–2 句說明]
```

**必須帶具體數字**：不只說「提升性能」，要說「Pass@3 從 0.523 → 0.560（+3.7%）」。

---

## 3. 研究背景與動機（必寫，# 一、）

- 說清楚這個領域的「缺口」（gap），用條列格式
- 不超過 4 個 gap，每個 gap 一行，格式：`- **Gap N：標題**：一句話說明為何是缺口`
- 說明本文欲解決的具體痛點，以及為什麼現有方法解決不了

---

## 4. 核心演算法直覺（必寫，# 二、）

### 2.1 核心概念（必寫）

**目的：讓讀者在進入流程細節前，先抓住論文最想傳達的一個想法。**

- 用 1–2 句話說出論文的核心洞見（不是方法步驟，而是「為什麼這樣想」）
- 用生活比喻或類比打底（會議紀錄、行李箱、打散再收納）
- 說清楚「它跟直接做有什麼不一樣」，假設讀者是工程師、不假設讀者看過論文

**核心圖表（必找）**：從論文中找出最能代表核心概念的 1 張圖（通常是 Figure 1 或架構總覽圖），緊接在白話說明後放置，並附上白話解釋：

```markdown
![[arxiv_id_fig01.png]]
*Figure 1: 原始英文 caption*

> 白話解釋：這張圖在說明什麼、關鍵的對比或流程是什麼、讀者應該注意的地方
```

- 若論文沒有架構圖，用文字描述核心概念的結構關係
- 這裡的圖是「概念理解用」；在 `六、關鍵圖表解讀` 仍需有對應條目做完整解讀

### 2.2 演算法流程（必寫）

用 code block 寫端到端資料流，每個步驟一行，括號內說明「為什麼這樣做」：

```
輸入向量 x
→ 隨機旋轉 Πx        （讓各維度近似獨立，消除 outlier 影響）
→ 逐維 Lloyd-Max 量化  （對每個座標找最近 centroid，存 b-bit index）
→ 殘差 r = x - x̃     （MSE 修復後還有內積偏差需要補正）
→ 1-bit QJL(r)       （修正內積偏差，確保 unbiased 估計）
→ 輸出：index + sign vector + residual norm
```

### 2.3 與舊方法最大的不同（必寫，1–3 點）

| | 舊方法 | 本文方法 |
|--|--------|---------|
| 關鍵差異1 | ... | ... |
| 關鍵差異2 | ... | ... |

## 5. 方法細節（必寫，# 三、）

- 涵蓋：超參數、公式、演算法變體（如 mse 版 vs prod 版）
- 每個公式後面要有一句白話解釋

---

## 6. 實驗結果（必寫，# 四、）

- 用表格呈現主要對比數字
- 每張表格下方必須有一行 `> 重點：...` 說明最重要的 takeaway
- 包含：baseline 設定、主要指標、與 SOTA 的差距
- **若數字對比層次多，優先用 code block 呈現**（比多層表格更易讀）：

```
Zero-shot        → 平均 0.523
MTL (Trajectory) → 平均 0.534  (+1.1%)  ← 最原始，有負向轉移風險
MTL (Insight)    → 平均 0.560  (+3.7%)  ← 最抽象，效果最好
```

- 每個重要結果後補一行說明 `← 原因`，幫助讀者理解數字背後的邏輯

---

## 7. 主要發現（必寫，# 五、）

**目的：在看完數字之後，提煉出最重要、最反直覺的結論。**

- 每個子節以「發現本身」命名，而非「發現一、二、三」這種空洞標題
- 好的子節標題範例：`## 5.1 更強模型 ≠ 更多元想法`、`## 5.3 Coverage 低不代表輸`
- 每個發現：先給一個直覺對比表（舊直覺 vs. 論文發現），再說明原因
- 含有反直覺的發現要優先放前面
- 3–5 個子節

---

## 8. 實驗數據解讀（有圖就必寫，# 六、）

**定位：圖片說明整合進對應章節（緊接圖片後方），`六、` 只作索引，不重複解讀內容。**

### 圖片說明格式（條列式，放在對應章節的圖片後）

每張圖的說明緊接在 `![[filename]]` 下方，使用條列式：

```markdown
![[filename]]
*Figure N: 原始英文 caption*

- **圖在說什麼**：一句話說明圖的目的（比較什麼、展示什麼趨勢）
- **關鍵數字**：從圖中讀出最重要的 1–2 個數字或對比
- **為什麼是這個結果**：用一句話解釋背後的機制或原因
- **Takeaway**：這個結果對讀者的意義

（如有子 case 或多個 panel，用加粗標題 + 縮排列點展開：）
**Case A — 標題**
- 子項目 1
- 子項目 2
- **失敗點 / 關鍵點**：...
```

### 六章的寫法

```markdown
# 六、關鍵圖表解讀

所有圖表的解讀已整合進對應章節：Fig 1–2 → 2.1，Fig 3–4 → 5.1，（依實際章節填入）。
```

- 必須解讀（條列說明）：主要對比實驗圖、ablation 結果圖、error analysis 圖、case study 圖
- 裝飾性示意圖（無數字、無對比）不需要說明
- 每張圖只出現一次，放在最有助於理解的位置；其他章節用「見 Figure N」文字引用

---

## 9. 侷限與風險（# 七、）

用 `[!warning]` callout，至少 2 點：
- 理論假設不成立的情境
- 工程落地的挑戰
- 哪些任務/資料集上效果有限

---

## 10. 延伸應用（# 八、）

- **短期**：可以立刻套用的場景
- **中期**：需要工程整合的方向
- **長期**：未來研究可以怎麼延伸

---

## 11. 落地設計（選填，# 九、）

**當論文機制可以直接對應到自己的系統設計時**，在延伸應用後加入這一節，把論文的方法轉化成可執行的設計規範。

格式不固定，可以是：
- Schema 定義（JSON 欄位 + 說明）
- 系統流程（code block 描述資料流）
- 設計決策說明（為什麼這樣設計、與論文的對應關係）

**何時加、何時不加**：
- 論文方法可以直接落地自己的 KG / Agent 系統 → 加
- 純理論論文、或與當前工作無直接關聯 → 跳過

這一節是 Arthur 對論文的主動應用，不是論文內容的總結。

## 12. Callout 工具表

| Callout | 用途 |
|---------|------|
| `[!abstract]` | TL;DR 一句話總結 |
| `[!info]` | 演算法流程、背景知識 |
| `[!tip]` | 工程含義、應用價值 |
| `[!note]` | 補充說明、判讀提示 |
| `[!warning]` | 侷限、風險、假設不成立的條件 |
| `[!danger]` | 論文核心錯誤風險 / 無法複現的問題 |
| `[!quote]` | 論文原文重要引用 |

---

## 13. 多篇並行處理

收到多篇論文 URL 時，**圖片下載不可省略**，執行順序：

1. 並行抓取所有論文的 HTML / PDF
2. 並行下載所有論文的圖片（完成後才進入下一步）
3. 並行撰寫筆記，圖片 embed 使用已下載的檔名

---

## 14. 品質標準

1. **2 分鐘可判讀**：TL;DR + 研究背景讓人理解動機，演算法直覺讓人決定要不要深讀
2. **有具體數字**：不只說「更快」，要說「快多少倍、省多少 bytes」
3. **有批判性**：明確說理論假設的邊界條件和侷限
4. **工程視角**：說清楚落地的挑戰（有沒有開源、GPU kernel 難度）
5. **有速查表**：所有數字集中在最後
