# 論文筆記格式規範

每次整理 AI / 技術論文筆記，必須遵循以下結構。
核心原則：**先讓人看懂「它在做什麼」，再深入「為什麼這樣做」。**

> **語言、圖片判斷、速查表格式**見 CLAUDE.md 全域規範，本文不重複。

---

## 整體結構順序

```
1.  Frontmatter
2.  TL;DR（[!abstract] callout，一句話）
3.  一、核心演算法直覺（白話 + 流程圖 + 對比表）
4.  二、主要發現（3–5 個子節，以反直覺或最重要的結論命名）
5.  三、研究背景與動機
6.  四、方法細節
7.  五、實驗結果
8.  六、關鍵圖表解讀
9.  七、侷限與風險
10. 八、延伸應用
11. 九、落地設計（選填）— Arthur 自己的系統設計延伸
12. 附：關鍵數據速查表
```

**章節編號規範**：
- 主章節用中文數字：`# 一、` `# 二、` ... `# 九、`
- 子節用阿拉伯數字，對應主章節：`## 1.1` `## 1.2`、`## 4.1` `## 4.2`
- 範例：`# 四、方法細節` → `## 4.1 任務定義` → `## 4.2 核心指標`

> [!note] 設計邏輯
> 傳統學術順序（背景 → 方法 → 實驗）適合審稿人，不適合快速吸收。把「它在做什麼、效果多好」放最前，讓讀者在 2 分鐘內決定要不要繼續深讀。

## 1. Frontmatter（必填）

```yaml
---
title: 中文標題（論文名稱直譯或意譯皆可）
date: YYYY-MM-DD（arXiv 發布日期）
source: 會議/期刊名稱（如 ICLR 2026、arXiv）
authors: 第一作者, 第二作者 et al.（機構）
sector: 研究領域（如 LLM 推理 / 向量量化 / RL）
tags:
  - 核心技術1
  - 核心技術2
url: arXiv 或論文連結
---
```

**注意**：`authors` 欄位寫作者姓名（非 `speaker`），機構放括號內。若有多個連結（如知乎中文解析），加 `url_zh:` 欄位。

---

## 2. TL;DR（必寫，放在 frontmatter 正下方）

用 `[!abstract]` callout，一句話包含：**方法名稱** + **核心做法** + **最重要結果數字** + **與現有方法的對比**

```markdown
> [!abstract] 一句話總結
> [方法名] 用「[核心做法]」，在[限制條件]下，使 [指標] 從 X 提升至 Y（+N%），並以 [A] 擊敗使用 [B] 的既有方法。
```

**必須帶具體數字**：不只說「提升性能」，要說「Pass@3 從 0.523 → 0.560（+3.7%）」。

若論文沒有可量化結果（如純理論），改用：
```markdown
> [!abstract] 一句話總結
> [方法名] 提出「[核心機制]」，解決[具體問題]，核心貢獻是[1-2 句說明]。
```

## 3. 核心演算法直覺（必寫，# 一、）

### 3.1 白話解釋（2–4 段）
- 假設讀者是工程師，不假設讀者看過論文
- 用生活比喻或類比打底（會議紀錄、行李箱、打散再收納）
- 說清楚「它跟直接做有什麼不一樣」

### 3.2 演算法流程（必寫）

用 code block 寫端到端資料流，每個步驟一行，括號內說明「為什麼這樣做」：

```
輸入向量 x
→ 隨機旋轉 Πx        （讓各維度近似獨立，消除 outlier 影響）
→ 逐維 Lloyd-Max 量化  （對每個座標找最近 centroid，存 b-bit index）
→ 殘差 r = x - x̃     （MSE 修復後還有內積偏差需要補正）
→ 1-bit QJL(r)       （修正內積偏差，確保 unbiased 估計）
→ 輸出：index + sign vector + residual norm
```

**論文架構圖（若有）緊接在演算法流程之後放置**，讓讀者在看流程說明的同時可以對照圖示：

```markdown
![[arxiv_id_fig01.png]]
*Figure 1: 原始英文 caption*
```

### 3.3 與舊方法最大的不同（必寫，1–3 點）

| | 舊方法 | 本文方法 |
|--|--------|---------|
| 關鍵差異1 | ... | ... |
| 關鍵差異2 | ... | ... |

---

## 4. 主要發現（必寫，# 二、）

**目的：把論文最重要的結論前置，讓讀者在進入方法細節之前就抓到核心。**

- 每個子節以「發現本身」命名，而非「發現一、二、三」這種空洞標題
- 好的子節標題範例：`## 2.1 更強模型 ≠ 更多元想法`、`## 2.3 Agent 越多，不代表探索越廣`
- 每個發現：先給一個直覺對比表（舊直覺 vs. 論文發現），再說明原因
- 含有反直覺的發現要優先放前面

---

## 5. 關鍵圖表解讀（有圖就必寫，# 六、）

每張重要圖表一個條目：

```markdown
### Figure N（頁碼）：圖表標題

![[filename]]
*Figure N: 原始英文 caption（如有）*

（一段白話說明：這張圖在比較什麼、最重要的 takeaway、關鍵數字）
```

- 用自然段落說明，不強制拆成固定欄位
- 複雜圖表（多組對比）可加對比表輔助說明
- 必須解讀：方法架構圖、主要對比實驗圖、ablation 結果圖
- 裝飾性示意圖不需要

---

## 6. 研究背景與動機（# 三、）

- 說清楚這個領域的「缺口」（gap），用條列格式
- 不超過 4 個 gap，每個 gap 一行
- 說明本文欲解決的具體痛點

---

## 7. 方法細節（# 四、）

- 涵蓋：超參數、公式、演算法變體（如 mse 版 vs prod 版）
- 每個公式後面要有一句白話解釋

---

## 8. 實驗結果（# 五、）

- 用表格呈現主要對比數字
- 每張表格下方必須有一行 `> 重點：...` 說明最重要的 takeaway
- 包含：baseline 設定、主要指標、與 SOTA 的差距
- **若數字對比層次多，優先用 code block 呈現**（比多層表格更易讀）：

```
Zero-shot        → 平均 0.523
MTL (Trajectory) → 平均 0.534  (+1.1%)  ← 最原始，有負向轉移風險
MTL (Insight)    → 平均 0.560  (+3.7%)  ← 最抽象，效果最好
```

- 每個重要結果後補一行說明 `← 原因`，幫助讀者理解數字背後的邏輯

---

## 9. 侷限與風險（# 七、）

用 `[!warning]` callout，至少 2 點：
- 理論假設不成立的情境
- 工程落地的挑戰
- 哪些任務/資料集上效果有限

---

## 10. 延伸應用（# 八、）

- **短期**：可以立刻套用的場景
- **中期**：需要工程整合的方向
- **長期**：未來研究可以怎麼延伸

---

## 11. 落地設計（選填，# 九、）

**當論文機制可以直接對應到自己的系統設計時**，在延伸應用後加入這一節，把論文的方法轉化成可執行的設計規範。

格式不固定，可以是：
- Schema 定義（JSON 欄位 + 說明）
- 系統流程（code block 描述資料流）
- 設計決策說明（為什麼這樣設計、與論文的對應關係）

**何時加、何時不加**：
- 論文方法可以直接落地自己的 KG / Agent 系統 → 加
- 純理論論文、或與當前工作無直接關聯 → 跳過

這一節是 Arthur 對論文的主動應用，不是論文內容的總結。

## 12. Callout 工具表

| Callout | 用途 |
|---------|------|
| `[!abstract]` | TL;DR 一句話總結 |
| `[!info]` | 演算法流程、背景知識 |
| `[!tip]` | 工程含義、應用價值 |
| `[!note]` | 補充說明、判讀提示 |
| `[!warning]` | 侷限、風險、假設不成立的條件 |
| `[!danger]` | 論文核心錯誤風險 / 無法複現的問題 |
| `[!quote]` | 論文原文重要引用 |

---

## 13. 多篇並行處理

收到多篇論文 URL 時，**圖片下載不可省略**，執行順序：

1. 並行抓取所有論文的 HTML / PDF
2. 並行下載所有論文的圖片（完成後才進入下一步）
3. 並行撰寫筆記，圖片 embed 使用已下載的檔名

---

## 14. 品質標準

1. **2 分鐘可判讀**：TL;DR + 演算法直覺讓人決定要不要深讀
2. **有具體數字**：不只說「更快」，要說「快多少倍、省多少 bytes」
3. **有批判性**：明確說理論假設的邊界條件和侷限
4. **工程視角**：說清楚落地的挑戰（有沒有開源、GPU kernel 難度）
5. **有速查表**：所有數字集中在最後
